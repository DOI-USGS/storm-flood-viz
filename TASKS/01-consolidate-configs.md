# Task 01 — Consolidate viz and storm configs into per-storm config files

Branch: `refactor/01-consolidate-configs`

## Goal
Move all per-storm parameters (storm metadata, dates, bbox, projection, timezone, landfall) and viz parameters (palettes, fonts, plot dimensions, toggles) out of `0_config.R` and into a single, declarative config file per storm so future events can be regenerated by swapping one file.

## Why
- `0_config.R` currently mixes pipeline plumbing, storm-specific values (e.g. Helene `stn_event = 346`, `2024-09-24` dates, landfall time), and viz tuning (palettes, plot shifts) as 25+ separate `tar_target()`s.
- Per REFACTOR.md priority #1: "consolidate viz and storm configs into config files for each change" so storm setup is one edit, not many.

## Affected files
- [0_config.R](0_config.R) — strip storm/viz literals; load from config
- [_targets.R](_targets.R) — wire config loader into the pipeline
- New: `config/helene.yml` (or `.R`) — concrete config for the existing Helene run
- New: `config/_template.yml` — annotated template for future storms
- New: `1_fetch/src/load_storm_config.R` — small reader/validator

## Stepwise plan
1. Inventory every `p0_*` target in [0_config.R](0_config.R) and bucket each as: `storm`, `viz`, or `pipeline-constant`.
2. Decide format (YAML preferred for human edits; R list acceptable). Single file per storm.
3. Build `load_storm_config()` that returns a named list and validates required keys (storm_name, storm_code, dates, bbox, proj, landfall_time, timezone, palettes, viz_config_df fields).
4. Replace literals in `0_config.R` with `tar_target()`s that pull from the loaded config; keep target names stable so `1_fetch.R`/`2_process.R`/`3_visualize.R` need no edits.
5. Write `config/helene.yml` reproducing today's values exactly.
6. Document the swap workflow (one-line README addition or comment block in template).

## Success criteria
- Re-running `tar_make()` with `config/helene.yml` produces byte-identical (or pixel-identical) outputs to current main.
- A new storm can be configured by copying the template, editing values, and pointing the pipeline at the new file — no edits to `0_config.R` needed.
- No downstream phase files (`1_fetch.R`, `2_process.R`, `3_visualize.R`) need to change.

## Test
- A second config file (`config/_template.yml` filled with placeholder values) loads without error and produces the expected list shape.
